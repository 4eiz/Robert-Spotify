# Проверка безопасности — 27 октября 2026

Проверен код приложения и локальная производственная сборка. Это не гарантия отсутствия любых уязвимостей: реальный сервер, reverse proxy, PostgreSQL и живой Telegram ещё не проверены.

## Исправления

- Python-аудит первоначально обнаружил уязвимые версии DRF, cryptography, pip и setuptools. Установлены DRF 3.18.3, cryptography 50.0.2, pip 26.2.2 и setuptools 84.2.1. Ограничения версий обновлены в requirements и Dockerfile. Повторный pip-audit: известных уязвимостей нет (48 пакетов, включая инструменты проверки). npm audit: известных уязвимостей нет. Отсутствие записей в базе advisory не означает абсолютную безопасность.
- Telegram OIDC проверяет RS256-подпись реальными криптографическими примитивами, issuer, audience, expiry, nonce, state и разрешённый ID. Попытка входа действует 10 минут, callback одноразовый. Тесты используют локально подписанные токены; ключи Telegram/JWKS и обмен кодом подменены в тесте, живой вход пока не настроен.
- Сессия владельца проверяется на каждом приватном API. Локальный вход допустим только в DEBUG при явном флаге и loopback-адресе. Compose принудительно выключает локальный вход. У Django-пользователя нет пригодного пароля для альтернативного входа.
- POST/PATCH/DELETE защищены CSRF, в том числе получение пароля. Сессия HTTPOnly, SameSite=Lax, срок 12 часов; в production cookies Secure, HTTPS обязателен. API выдаёт только JSON, данные не кешируются, вход и API-ответы имеют no-store.
- Пароли аккаунтов хранятся зашифрованно Fernet. В списочных ответах нет пароля или ciphertext. Отдельное раскрытие записывается в журнал. Значимые пробелы в паролях сохраняются. UI не пишет секреты в localStorage; показанный пароль очищается через 30 секунд и при скрытии вкладки/потере фокуса окна. Скопированный пароль остаётся в системном буфере до его замены пользователем или ОС.
- CSP с уникальным nonce на каждый ответ: без unsafe-inline/unsafe-eval для скриптов в production, frame-ancestors none, object-src none, base-uri none. Неподписанный скрипт, внедрённый в HTML-ответ, блокируется браузером; обычная загрузка приложения продолжает работать. Для стилей оставлен unsafe-inline: интерфейс использует вычисляемые CSS-стили. В development разрешён unsafe-eval для Next.js, в production его нет.
- X-Frame-Options DENY, nosniff, Referrer-Policy и Permissions-Policy запрещают встраивание, камеру, микрофон, геолокацию и Payment API. Размер запроса ограничен; устранён известный обход лимита обновлением DRF.
- Один активный владелец обеспечен формой, API и уникальным ограничением БД. Проверки лимита семьи повторяются под блокировкой в транзакции. Продление вычисляет дату на сервере, присланная клиентом произвольная дата не используется.

## Доказательства

Контраст вторичного текста проверен расчётом: светлая тема — 5.76:1 на белом и 5.40:1 на основном фоне; тёмная — 8.41:1 на карточках.

- 40 серверных тестов прошли: права доступа, CSRF, секреты, единственный владелец, OIDC с валидной/поддельной подписью, неправильные claims/ID, срок попытки входа, повторный callback, выход, расчёты и API.
- TypeScript и production build прошли.
- Chrome/Playwright: ПК 1440 px и телефон 390 px; темы, валюты, формы, условные цены, продление по месяцам, скелетон. Нет JS-ошибок и переполнения документа.
- Отдельный production browser test подтвердил CSP/nonces, блокировку HTML script injection и запрет анонимного доступа к API.
- `check --deploy` с DEBUG=0: только W005 и W021. HSTS для текущего хоста включён на год. includeSubDomains и preload намеренно выключены: их нельзя включать заочно для чужих/ещё не проверенных поддоменов существующего домена.

## До развёртывания

Проверить PostgreSQL и Docker на рабочем сервере; установить HTTPS и правильный домен; настроить и проверить настоящий Telegram Login и уведомления. Reverse proxy должен перезаписывать X-Forwarded-Proto, не доверяя входному заголовку клиента. Backend и БД не публиковать наружу (Compose этого не делает). Публичный порт frontend привязан к 127.0.0.1 для существующего reverse proxy.

Секреты .env и резервные копии БД защищать правами ОС. Ключ Fernet сохранять отдельно от дампа. Не запускать DEBUG/локальный вход на публичном интерфейсе. Эти условия влияют на безопасность и не проверяются одним тестом приложения.
